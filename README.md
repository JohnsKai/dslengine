## 提示词工程技巧
**1. 分阶段、模块化提示词**  
按骨架 → 核心接口 → DTO → 节点实现 → 引擎 → 测试 拆分任务。  

一定要先设计，可以先和ai讨论自己的架构设计(白嫖ds)，然后一步步演化，最终得到一个自己相对满意的设计，然后自己先大概敲一下提示词，甚至可以直接让ai给出提示词，觉得没什么问题，就无脑交给cursor做就行了
示例：`任务1：创建 Maven 项目，pom.xml 包含 MQTT、Aviator、Jackson、SLF4J，JDK 8。`

**2. 使用约束性语言，避免歧义**  
使用“必须”、“不要”等强约束词，明确列出禁止的 API  
示例：`不要使用 Map<String,Object> 作为上下文；必须用 TypedContext+Key<T>。禁止 Java 9+ 语法。`

**3. 给出输入输出示例**  
提供 JSON 示例和期望的 DTO 结构。  
示例：`规则 JSON：{ "id":"lightRule", "startNodeId":"onEvent", "nodes":[...] } 请生成 RuleDefinition 类。`

**4. 要求只输出变更代码块（diff 风格）**  
节省 token，避免重复大段代码。  
示例：`只输出修改的方法，不要重复整个类。`

**5. 使用 Cursor 的 `@` 引用文件**  
在 Composer/Chat 中用 `@文件名` 让 AI 直接读取现有代码。还有其他@ 用法也是同此。
示例：`@TypedContext.java 增加 toMap() 方法。`

**6. 迭代修复：把错误信息直接喂给 AI**  
复制完整错误栈，让 AI 分析修复。  
示例：`编译错误：class file version 55.0 ... only recognizes 52.0。如何解决？`

## Cursor Rules 配置
项目根目录 `.cursorrules` 固化规范。有效字段示例：
```text
# 项目背景
技术栈：Java + Maven，IoT 规则引擎，目标 TPS ≥ 800。

# 代码规范
- 所有 public 类必须有 Javadoc。
- 使用 SLF4J 日志，不用 System.out。
- 异常处理：自定义异常直接抛出，其他记录 error。

# 避免事项
- 不要使用 Map<String,Object> 作为上下文。
- MQTT 必须异步，禁止在 onEvent 中同步等待。

# 节省 token 要求
- 回复时只生成必要的代码，不要解释整个文件。
- 修改已有类时只输出 diff。

## 开发流程与协作模式
## 性能测试与压测
## 经验总结与避坑指南
```

## 开发流程与协作模式

**1.典型流程**

这个也是相当于自己和ai对话思考架构演进的过程

编写 .cursorrules → 2. 生成 DTO 和接口 → 3. 实现核心节点 → 4. 编写引擎 → 5. 手工压测 → 6. 版本管理

```text
  [具体需求]：......
  
  [约束]：遵循 .cursorrules，只输出变更代码块。
```


## 性能测试与压测
**手工压测 `ManualLoadTest.java` 关键点：**

- 模拟设备控制耗时：Thread.sleep(10)。
 
- 并发模型：CountDownLatch 等待所有事件完成，统计总耗时和 TPS。

- 线程池：发送线程池 + 引擎内部线程池分离。
 
- 目标 TPS：800，实测普通笔记本可达 2000+（不含 sleep）

**压测提示词示例**

`请生成手工压测类，发送 800 个事件，每个动作耗时 sleep(10) ms，使用 CountDownLatch 统计 TPS 和平均延迟。`

## 经验总结与避坑指南

**有效做法**

- 先定 Rules，再写代码，减少返工。

- 小步提交，每生成一个类就编译验证。

- 善用 @ 引用，精确控制上下文。

- 压测提前做，发现性能瓶颈。

**常见陷阱**

- 在 onEvent 中同步阻塞：必须异步化。

- 规则 JSON 配置错误：缺少 nextTrue / nextFalse 导致中断。

- 忘记 EventNotMatchedException：异常被吞掉，难以调试。
